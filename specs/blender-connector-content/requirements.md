# CONN-BLENDER-CONNECTOR-CONTENT — Requirements

Governing spec: [spec.md](spec.md).

Each row is one requirement. A row names the file it touches and the test that proves it. The generator sets each row's state in `status.json`.

| ID | Requirement | Acceptance |
|---|---|---|
| `CONN-BLENDER-CONNECTOR-CONTENT-R001` | **Default content.** `pyproject.toml` declares `blender-connector` as the single `scion_sdk.connector` entry point and `blender_connector.prompts` as a prompt provider. The server lists the packaged `skill://` and `ontology://` resources and the packaged prompts with no `content=` argument. Proving test: `tests/test_content_surfaces.py`. Caller chain: the `blender-connector` console script loads the `scion_sdk.connector` entry point `blender_connector:connector` → `blender_connector/__init__.py` (a `Connector` with no `content=` argument) → the SDK default content registration serves `skill://`, `ontology://` and the prompts from the package directories. Shape: tests build the server from `blender_connector` and list resources and prompts over the packaged `blender_connector/skills`, `blender_connector/ontology` and `blender_connector/prompts` directories. The upstream is disabled for the test, so no child starts. | `resources/list` includes `skill://blender/SKILL.md` and `ontology://blender-connector/blender.ttl`; `prompts/list` includes each of the nine packaged prompts. Test: `tests/test_content_surfaces.py::test_default_content_surfaces`. |
| `CONN-BLENDER-CONNECTOR-CONTENT-R002` | **Authored app source.** Subsystem: content tier, source. `content/apps/blender.yml` holds the app name `blender`, an authored summary, eight domain classes each naming one parent, and nine functionalities each with a `name`, a `description`, an ordered `tools` list and `steps`. The functionality set partitions the full served tool surface: every tool in the committed snapshot belongs to at least one functionality. A snapshot tool that belongs to no functionality is reported by the generator as unassigned; it is not a failure, because the skill table still lists it. The snapshot is taken with a plain MCP client (no app extensions), the surface the connector's proxy serves to a host agent over plain MCP. Caller chain: the loader `load_app_source` in `blender_connector/content_gen/sources.py` reads the file; the generator and the partition check consume it. Shape: one YAML file; no generation logic in this row. Refusal: none at parse time beyond YAML errors. Depends on: `CONN-BLENDER-CONNECTOR-R001`. | `tests/test_content_drift.py::test_functionality_partition_covers_the_snapshot`. The partition of the committed source over the committed snapshot leaves no unassigned tool. |
| `CONN-BLENDER-CONNECTOR-CONTENT-R003` | **Generate the ontology.** Subsystem: content tier, ontology. `render_ontology` writes `blender_connector/ontology/blender.ttl`. The file holds an `owl:Ontology` node with the IRI `http://knuckles.team/kg/blender`; the pack classes `app:BlenderApp` as a subclass of `:Application`, `app:BlenderTool` as a subclass of `:Tool` and `app:BlenderUseCase` as a subclass of `:Task`, where `app:` is `http://knuckles.team/kg/blender#`; the eight domain classes from the source, each extending its parent (`:Document`, `:Artifact`, `:CreativeWork`); and the individuals: one `app:BlenderApp` with `app:appNamespace "blender"` and `app:appVersion` from the snapshot, and one `app:BlenderUseCase` per functionality with `app:forApp` and one `app:usesToolName` per namespaced tool. The parent catalog a serving engine composes depends on the engine generation, so each class declares `rdfs:subClassOf` to its core parent under both namespaces: the retired `http://knuckles.team/kg#` and the core module `https://knuckles-team.github.io/ontology/core#`. The file declares no `owl:imports` and redeclares no core class. Refusal: `CONTENT_PARENT_UNKNOWN` when a class names a parent outside the allowed set. Caller chain: `scripts/generate_blender_content.py` → `render_ontology` in `blender_connector/content_gen/ontology.py` → the file; the server lists the file as an `ontology://` resource. Shape: a pure function from the app source and the snapshot to Turtle text. Reuse `CONN-BLENDER-CONNECTOR-CONTENT-R001` for listing. Depends on: `CONN-BLENDER-CONNECTOR-CONTENT-R002`, `MEDULLA-TYPED-PACKS-R071.2`, `MEDULLA-TYPED-PACKS-R102.3`, `MEDULLA-TYPED-PACKS-R105`. | `tests/test_content_drift.py::test_committed_content_matches_snapshot`. The committed ontology file matches the render of its sources byte for byte, so the dual parent edges and the individuals are pinned by the gate. |
| `CONN-BLENDER-CONNECTOR-CONTENT-R004` | **Generate the skill.** Subsystem: content tier, skills. `render_skill` writes `blender_connector/skills/blender/SKILL.md`. The front matter holds `name` and `description`. The body holds: when to use the app; the activation note (the namespace `blender` is active by default; under lazy activation, call `registry_activate` first); a tool table generated from the snapshot with every tool named `blender_<tool>` and its description; and the functionality list that links to the prompt names. The table holds every snapshot tool exactly once, so a new upstream tool is a visible change. Refusal: `CONTENT_SKILL_TOOL_UNKNOWN` when an authored section names a tool that the snapshot lacks. Caller chain: `scripts/generate_blender_content.py` → `render_skill` in `blender_connector/content_gen/skill.py`; the listing runs through `build_server`. Shape: a pure function from the app source and the snapshot to Markdown. Depends on: `CONN-BLENDER-CONNECTOR-CONTENT-R002`, `CONN-BLENDER-CONNECTOR-CONTENT-R006`. | `tests/test_content_drift.py::test_committed_content_matches_snapshot`. The committed skill matches the render, which pins the full tool table against the committed snapshot. |
| `CONN-BLENDER-CONNECTOR-CONTENT-R005` | **Generate a prompt per functionality.** Subsystem: content tier, prompts. For each of the nine functionalities the generator writes `blender_connector/prompts/blender-<functionality>.json` with the key set of the exemplar prompt: `task`, `description`, `instructions.core_directive`, `instructions.quality_checklist`, `tools` and `requires_namespace`. The prompt tells the model that the namespace `blender` is active by default and to activate it first under lazy activation. It names only tools that the snapshot lists, each as `blender_<tool>`, in the functionality's order. `requires_namespace` is `blender`. Each functionality is also one `app:BlenderUseCase` individual in the ontology (`CONN-BLENDER-CONNECTOR-CONTENT-R003`). Refusal: `CONTENT_PROMPT_TOOL_UNKNOWN` for a tool absent from the snapshot. Caller chain: `scripts/generate_blender_content.py` → `render_prompts` in `blender_connector/content_gen/prompts.py`; the server lists each file through the `scion_sdk.prompt_providers` entry point. Shape: a pure function to a name-to-text mapping; reuse the key set of the exemplar prompt. Depends on: `CONN-BLENDER-CONNECTOR-CONTENT-R002`, `CONN-BLENDER-CONNECTOR-CONTENT-R006`. | `tests/test_content_drift.py::test_render_refuses_an_unknown_tool`. A functionality that names a tool the snapshot lacks fails with `CONTENT_PROMPT_TOOL_UNKNOWN`. The nine committed files match the render through the drift gate. |
| `CONN-BLENDER-CONNECTOR-CONTENT-R006` | **Content generator and tool snapshot.** Subsystem: content tier, generator. `scripts/generate_blender_content.py` holds the modes `--refresh`, `--write`, `--check` and `--live`. `--refresh` starts `mcp-for-blender`, reads `tools/list` and the server version, and writes `content/snapshots/blender.tools.json`: the app name, the version, and the tools sorted by name with each name, description and input schema. It starts a real binary, so it runs on a host that has one. `--write` renders the ontology, the skill and the prompts from `content/apps/blender.yml` and the snapshot into the package directories. `--check` renders in memory and compares bytes with the committed files. The tool names in a snapshot are the upstream names; the renderers add the namespace prefix when they write content. Knob: `--timeout` 30 seconds (range 5 to 300). Refusals: `CONTENT_SNAPSHOT_MISSING` when a non-refresh run has no snapshot, and `CONTENT_DRIFT` from the check mode. Caller chain: operator or CI runs the script → `main` → the three render functions of `CONN-BLENDER-CONNECTOR-CONTENT-R003` to `CONN-BLENDER-CONNECTOR-CONTENT-R005`. Shape: one script and the package `blender_connector/content_gen/` with `sources`, `skill`, `ontology`, `prompts` and `errors`; reuse the SDK client for `--refresh`. Depends on: `CONN-BLENDER-CONNECTOR-R001`. | `tests/test_content_drift.py::test_committed_content_matches_snapshot`. The committed content equals the render of its sources, so two runs give identical bytes. A run without the snapshot fails with `CONTENT_SNAPSHOT_MISSING`. |
| `CONN-BLENDER-CONNECTOR-CONTENT-R007` | **Drift gate for generated content.** Subsystem: content tier, drift. The offline gate runs `generate_blender_content.py --check` in CI. It fails when any committed ontology, skill or prompt differs from the render of its sources, with the finding `CONTENT_DRIFT` that names the drifted file. This gate needs no upstream. The live gate runs `--live` on a host with the binary: it refreshes in memory and compares each tool fingerprint with the committed snapshot. The fingerprint is the SDK `compatibility_fingerprint` of each tool (`SCION-CONNECTOR-CONTROL-R914.11`). A difference fails with `CONTENT_SNAPSHOT_STALE` and lists the added, removed and changed tool names. The live gate runs after each upstream update, together with `blender-connector-probe` (`CONN-BLENDER-CONNECTOR-R003`). Caller chain: the connector pipeline's pre-commit wave calls the offline gate; the host job calls the live gate. Shape: the `--check` and `--live` modes of the script; the offline gate is the pre-commit hook `content-drift` that the pipeline runs in CI. Depends on: `CONN-BLENDER-CONNECTOR-CONTENT-R006`. | `tests/test_content_drift.py::test_committed_content_matches_snapshot`. The offline gate passes as a subprocess against the committed content and fails on a drift. The live gate is an operator step; a host without the binary records the gap rather than a false pass. |
